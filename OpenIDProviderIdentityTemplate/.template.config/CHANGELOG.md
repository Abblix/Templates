# Changelog: abblix-oidc-server

What changed in the project that the OpenIDProviderIdentityTemplate creates, version by version. The versions are those of the Abblix.Templates package that ships the template.

## 3.1.0

- The tenant and the clients it declares live in `oidc.db`, in the `Tenants` and `TenantClients` tables, which the server reads through `OidcStore/DurableTenantStore.cs`. `Program.cs` no longer defines the issuer, its resources or its login page, and `appsettings.Development.json` no longer declares `Oidc:Clients`. A new database starts with the tenant and the demo clients `test_client` and `console_client`, written by `EnsureCreated` from the seed data in `OidcStore/InitialData.cs`. In 3.0.0 the configured clients were copied into the `Clients` table on the first run, and a later edit to the configuration was not applied.
- A row added, changed or deleted in `Tenants` or `TenantClients` is served as such within `OidcOptions.RefreshTenantsEvery`, without a restart. A tenant whose rows cannot be read, such as a `Payload` that is not valid JSON, is left out and logged as an error naming the tenant, the row and the reason, and so is a tenant the server's checks refuse, such as one with a client secret hash of the wrong length; the provider keeps running and answers that tenant's requests as for no tenant until the row is fixed. Each tenant is an issuer, and serving more than one issuer needs an Abblix OIDC Server license: set it as `OidcOptions.LicenseJwt` in the options delegate `Program.cs` passes to `AddOidcServices`, as [Licensing](https://www.abblix.com/en/docs/multi-tenancy#license) describes. Without one, the server counts tenants in the order of their first requests and refuses those beyond the first.
- The demo clients' secret is generated for each project as it is created, or set with `--client-secret`. It is held in `OidcStore/InitialData.cs` and `requests.http`. The secret `secret` that 3.0.0 published with the template opens nothing.
- A tenant's signing key is created by `OidcStore/SigningKeyOpening.cs` before the server first serves the tenant, so a tenant added to the database while the provider runs gets one too. The startup code no longer creates it.
- The pipeline calls `app.UseMultiTenancy()`, which the server requires once its tenants come from a store of the host's own. A request is matched to its tenant by host name and path, so the provider answers at the issuer's host name only: `127.0.0.1` in place of `localhost` reaches no tenant.
- `dotnet publish` copies `appsettings.Development.json` again: it holds only logging levels now.

## 3.0.0

First release of this template.

- The short name `abblix-oidc-server` now creates this provider. In 2.x it created the in-memory provider, which is now `abblix-oidc-server-gettingstarted`; a project created from that one is described in its own changelog.
- The short names `oidc-server`, `oauth2-server` and `openidconnect` create this provider too. 2.x listed them under `aliases`, a property the template engine does not read, so `dotnet new oidc-server` found no template.
- An OpenID Provider on ASP.NET Core and Abblix OIDC Server 3.0.0 for .NET 11, serving one issuer declared as a tenant. The issuer is fixed in `Program.cs` as `https://localhost:<port>`; before deploying, set `Issuer` to the provider's public address, or clients reject its tokens. In 2.x, `abblix-oidc-server` set no issuer and took it from the host each request arrived on.
- `--host` picks the host style. `minimal`, the default, maps the OpenID endpoints with `app.MapOidcEndpoints()` from Abblix.Oidc.Server.MinimalApi and serves the home, error and login pages from `MinimalApiPages.cs`, with no MVC controllers or Razor views. `mvc` serves the endpoints with `app.MapOidcControllers()` from Abblix.Oidc.Server.Mvc and the pages as controllers with views. Both login pages check their antiforgery token in the handler, so a form submitted from another site is refused and a form opened in another tab before a sign-in is shown again; a form without an email or a password shows "Invalid username or password", and a sign-in with no authorization request to resume goes to the home page.
- ASP.NET Core Identity keeps the users on EF Core 11 with SQLite and stores their passwords as salted hashes.
- Client registrations and the signing key are stored in SQLite too, so a restart keeps them and tokens issued before it still validate. The signing key is protected with ASP.NET Core Data Protection, whose key ring is a local folder; a build warning says what a real deployment uses instead.
- Clients are read from the `Oidc:Clients` configuration section, and only `appsettings.Development.json` declares any: `test_client` for the authorization code flow with PKCE and refresh tokens, redirecting first to the demo client's pages in this project and then to `https://localhost:5002` for a client application of your own, and `console_client` for the client credentials grant only, which gets no token for the registered `weather` API. Both use the secret `secret`, published with the template. `dotnet publish` does not copy `appsettings.Development.json`.
- Configured clients are seeded into `oidc.db` at startup. The server's own client checks judge them first, and a client they refuse stops startup with a message naming `Oidc:Clients`. A seeded row stays in the database whichever environment later runs on it, and a later edit to its configuration is not applied: the host logs a warning naming the client and the row to delete. A build warning says to delete the demo clients' rows, or start from a database never run in Development, before a real deployment.
- `requests.http`, to send from Visual Studio, JetBrains Rider or VS Code against the running provider: the discovery document, the published keys, an access token for `console_client` and introspection of that token. Token introspection (RFC 7662) is switched on with `AddIntrospection()` and advertised in the discovery document.
- `--https-port` sets the HTTPS port the provider is served on and names in its issuer. When it is omitted or 0, a port free on the machine is picked at random between 7000 and 7300 as the project is created.
- `--user` seeds a development sample user into the Identity store, and `--password` sets its password. The `--user` value is both the user's email address and login, so it must be a valid email address: Identity requires one, and a value such as `dev` stops the first run with an error. Without `--password`, a random password is generated and printed once on the console at first run, which then waits for Enter on an interactive console so the password can be copied. Without `--user`, the user is `demo@example.com`; with `--user ""`, no user is seeded. The user is seeded only in Development.
- The demo client's pages, served in Development from `DemoClient.cs`: the home page starts a sign-in as `test_client` with a fresh state and PKCE verifier, and after the login page the browser lands on a page of the project that shows the code, the verifier and the token request, with a button to sign out. `requests.http` then exchanges the code, reads the user's claims and refreshes the tokens.
- `EndSessionPages.cs` answers the end-session endpoint with a page asking the user to confirm a sign-out that carries no ID token, and a page saying they are signed out when no client asked to be sent back, instead of the library's JSON and empty answers.
- A `.gitignore` keeps `users.db`, `oidc.db`, the `dataprotection-keys` folder, which decrypts the signing key stored in `oidc.db`, and the build output out of a commit.
- EF Core's SQL commands are logged at Warning, so the first run's console shows the generated password rather than a page of `CREATE TABLE`.
- Building the project needs Node.js and npm. The build bundles Bootstrap into `wwwroot/lib` with Vite, again whenever the client sources are newer than the bundle, and first installs the npm packages with `npm ci`, exactly as `ClientAssets/package-lock.json` records them, whenever that lock is newer than the last install. A new project has neither a bundle nor an install, so its first build always runs both. The 2.x provider needed no Node.js.
- The Visual Studio New Project dialog shows the template with the Abblix icon and proposes `OpenIDProvider` as the project name. `ide.host.json` marks `--host`, `--https-port`, `--user` and `--password` as options for that dialog to show.
